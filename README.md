# Apple Tree Life Cycle Portal

The **Apple Tree Life Cycle Portal** hosts the natural life cycle, the orchard life cycle and the annual reproductive cycle. Stage and sub-stage characteristics are structured according to four dimensions. For orchard management operations, the portal integrates links to a list of relevant third-party databases and guidelines. For apple tree research, all references used throughout the life cycle are cited and traceable within the portal for further exploration and validation.

You can run the portal locally using the instructions below, or access the publicly available version at:

🔗 [https://applelifecycle-3094d65c1fea.herokuapp.com/](https://applelifecycle-3094d65c1fea.herokuapp.com/)

## What the portal contains

| | |
|---|---|
| BBCH stages and sub-stages | 57 |
| Management operations | 487 |
| Operation citations | 1,259 across 58 distinct sources |
| Key measurements | 490 |
| Measurement protocols | 85 in 11 categories |
| Bibliographic references | 491 |

Every management operation carries at least one citation to the guide, manual or paper it came from, with a page number or section wherever the source is paginated.

## Reading the tables

Each life-cycle row has four dimensions — timing, observation, key measurement and suggested management — and four kinds of link:

- **`[1]`, `[2]` citation markers** open a small card anchored beside the link, showing the full reference.
- **Key measurements** are grouped by category; clicking one opens its **measurement protocol** in a right-hand panel, with a back link to the category list.
- **`Table …` markers** open the suggested-management guide for that stage in a centred window.
- **`[Details]`** inside that guide opens the source list on top of it, so the guide stays visible behind.

All windows close with `×`, `Escape`, or a click outside.

## Running locally

Requires Node 18+ and Docker.

```bash
git clone https://github.com/lily214754/AppleLifecycle.git
cd AppleLifecycle
npm install

cp .env.example .env      # points at the local container; no edits needed
docker compose up -d db   # Postgres 15 on port 55432
npm start                 # http://localhost:3000
```

Then open <http://localhost:3000/tree_lifecycle?env=orchard>.

To run the app in a container alongside the database instead, use `docker compose up`.

## How the database is built

There is no ORM and no migration runner at boot. `app/config/db.js` executes a fixed, ordered list of SQL files every time the server starts, and the order matters:

1. **`database.sql`** — creates `reference_data`; skipped if the table already exists.
2. **`natural.sql`** — drops and recreates the stage tables and everything that points at them, then seeds the base life-cycle content. Because this drops tables, it must run before anything that references them.
3. **`protocol.sql`** — the 85 measurement protocols, their 11 categories, and the stage links. Generated by `tools/build_protocol_sql.py`; edit the generator, not this file.
4. **`added_operations_*.sql`** — one pass per source reviewed, each adding operations and citations.
5. **`fix_*.sql`** — corrections applied after all content is loaded: link replacements, stage-timing corrections, duplicate merges, and a final integrity pass.

Every pass is idempotent, so a restart converges on the same state rather than accumulating rows. `migrations/` holds standalone copies of the schema changes for applying to an existing database without a full rebuild.

**This means the content tables are rebuilt from source on every boot.** Data added through the API at runtime will not survive a restart. That is deliberate — the SQL files are the source of truth, and the deployed database is reproducible from the repository alone.

## Layout

```
app/
  app.js                 Express server, static caching, table-fragment routes
  config/
    db.js                connection pool + the ordered boot sequence
    *.sql                schema, seed data, per-source passes, fixes
  models/                SQL queries
  routes/                /api endpoints
  public/                scripts.js, style.css, table fragments, vendored jQuery
  templates/             page shells
  data/tablesData.json   the life-cycle table rows
migrations/              standalone schema migrations
tools/                   generators (protocol SQL from the source tables)
```

### One thing to know before editing `tablesData.json`

Each row's suggested-management cell links its operations with a `ref{STAGECODE}` marker. **An operation whose stage has no such marker is unreachable in the browser**, even though it is present and valid in the database. If you add operations at a new stage, add the marker to that stage's row in the same change, and confirm the counts behind every marker still sum to the total operation count.

## Configuration

| Variable | Purpose |
|---|---|

| `PGSSL` | Set to `disable` for a local container. Leave unset in hosting so TLS stays on. |

## Sources

Operations are drawn from published orchard management guides — among them the Australian Apple and Pear IPDM Manual, the NSW Orchard Plant Protection Guide, Penn State, Oregon State, Midwest, New Jersey and Southeast US production guides, APAL Future Orchards material, and *Apples: Botany, Production and Uses*.

A smaller set of operations is cited to peer-reviewed literature, identified in the portal by a DOI link rather than a guide URL. These cover topics the grower guides do not: end-of-productive-life and replant decisions, the measured efficacy of sunburn mitigation, and the pollination evidence on wild bees and pollen limitation.

Guides are linked to their publishers' online copies. Several publishers return `403` to automated requests while serving the same URL normally in a browser; those links are correct despite what a link checker reports.

## Deployment

Deployed on Heroku from the `main` branch of this repository. There is no `Procfile`; the Node buildpack runs `npm start`. Set `DATABASE_URL` to the managed Postgres add-on and leave `PGSSL` unset.

The server binds its port immediately and runs the SQL boot sequence in the background, so a slow rebuild does not cause a boot timeout.
